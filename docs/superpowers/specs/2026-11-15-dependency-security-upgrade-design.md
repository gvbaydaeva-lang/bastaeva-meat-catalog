# Обновление зависимостей и устранение уязвимостей

## Намерение

Уменьшить риск зависимостей в статическом каталоге ИП Бастаева А.Д., сохранив текущие маршруты, пустой подтверждённый ассортимент, дизайн, SEO-политику и GitHub Pages workflow.

## Цели

- Обновить уязвимые production- и development-зависимости до совместимых поддерживаемых версий.
- Отделить риски опубликованного статического сайта от рисков локального build/lint/test toolchain.
- Сохранить `output: "export"`, `trailingSlash`, GitHub Pages `basePath`, маршруты и контент без добавления товаров или фото.
- Проверить TypeScript, ESLint, тесты, локальную и GitHub Pages-сборку, audit и ключевые пользовательские маршруты.

## Не входит в задачу

- Новый дизайн, изменение структуры каталога, ассортимента, контактов или фотографий.
- Корзина, оплата, админка, Supabase, серверный runtime или изменение SEO-политики.
- `npm audit fix --force`, отключение audit/lint или искусственное скрытие предупреждений.

## Ограничения

- Production сейчас статический: опубликованный Pages-сайт не запускает Next server или Image Optimization API.
- Текущий audit показывает уязвимость Next/PostCSS в production-графе и дополнительные dev-only уязвимости Vitest/ESLint-графа.
- Workflow использует Node 20 и `npm ci`; lockfile должен оставаться воспроизводимым.

## Подходы

1. **Консервативный patch/minor upgrade в старом мажоре Next 14.** Минимальный diff, но текущие advisory требуют более нового Next и не закрываются полностью.
2. **Безопасная миграция на исправленный поддерживаемый Next 15/16 с React peer-версией и обновлением lint-команды.** Рекомендуется: закрывает критичный Next-граф, сохраняет App Router/static export, а изменения конфигурации можно ограничить package scripts и совместимостью ESLint.
3. **Оставить версии и только задокументировать, что Pages статический.** Недостаточно: production-граф продолжит содержать уязвимости, а задача просит их максимально устранить.

Выбран подход 2. Конкретная версия будет выбрана по актуальному npm metadata, peer-требованиям и результатам build/typecheck/lint/test. При несовместимости остановка будет на последней проверенной версии с конкретным объяснением.

## План проверки

1. Сравнить baseline audit и package graph в feature worktree.
2. Обновить package manifests/lockfile и, если требуется, lint-конфигурацию.
3. Запустить unit tests, typecheck, lint, production build и повторный audit.
4. Проверить экспортированные HTML/assets, basePath, robots/sitemap и локальный мобильный smoke ключевых маршрутов.
5. Просмотреть diff, запросить code review, push feature branch, создать PR, дождаться CI и Pages deployment, затем проверить публичные URL.
